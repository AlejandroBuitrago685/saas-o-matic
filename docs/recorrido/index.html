Presupuestos SaaS multi-divisa, de la regla al test

SaaS-O-Matic es la herramienta interna con la que un comercial da de alta clientes corporativos con su identificador fiscal validado y simula su suscripción por tramos, con impuestos y en la divisa que elija.

Abrir la demo Ver el repositorio Empezar el recorrido

La demo usa datos ficticios que se regeneran cada día. Para comprobar cada requisito con su test, la guía del evaluador.

Navegador Angular 22

Pinta la interfaz con signals y calcula la proyección con el mismo dominio que la API, sin esperar a la red (ADR-008).

Control de seguridad. CSP sin scripts ni estilos en línea, y ningún HTML insertado a mano: nada de innerHTML ni de bypassSecurityTrust*. RNF-SEC-06 · RNF-SEC-14

Dónde está

  • app.config.tsapps/web/src/app/
  • simulator.store.tsapps/web/src/app/features/simulator/

Cloudflare solo en la demo

Proxy y HTTPS delante del nginx del servidor de la demo pública. En local y con Docker Compose no existe.

Control de seguridad. El nginx del servidor recupera la IP real de CF-Connecting-IP solo si la conexión viene de Cloudflare, así que el límite de escrituras cuenta por cliente. RNF-SEC-08 · RNF-SEC-20

Dónde está

  • https.conf.templatedeploy/demo/nginx/
  • docker-compose.demo.ymldeploy/demo/

nginx web y proxy

Sirve la build de Angular y reenvía /api a la API: un único origen para la web y la API (ADR-012).

Control de seguridad. Cabeceras de seguridad y CSP de la web, y contenedores sin root, de solo lectura y con el puerto solo en 127.0.0.1. RNF-SEC-06 · RNF-SEC-16

Dónde está

  • nginx.confapps/web/nginx/
  • security-headers.confapps/web/nginx/

API Fastify rutas y casos de uso

Rutas finas que llaman a casos de uso; un único manejador de errores responde en formato RFC 9457 (ADR-009).

Control de seguridad. Límite de peticiones por IP, CORS con lista cerrada, errores sin detalles internos y logs sin datos personales. RNF-SEC-07 · RNF-SEC-08 · RNF-SEC-10 · RNF-SEC-11

Dónde está

  • app.tsapps/api/src/
  • rate-limit.tsapps/api/src/http/
  • error-handler.tsapps/api/src/http/

Contrato Zod esquemas compartidos

Los mismos esquemas validan las peticiones en la API, generan el OpenAPI y dan los tipos a la web (ADR-002).

Control de seguridad. Esquemas estrictos: un campo desconocido o un importe enviado por el cliente se rechazan con un 400. RNF-SEC-01 · RNF-SEC-03

Dónde está

  • simulations.tspackages/contract/src/

Dominio reglas puras

Precios por tramos, impuestos, redondeo, divisas y validación fiscal: funciones puras sin dependencias, con el 100 % de cobertura (ADR-001).

Control de seguridad. El servidor calcula todos los importes con estas funciones; nunca acepta uno del cliente. RNF-SEC-03

Dónde está

SQLite Drizzle

Clientes y simulaciones; cada simulación guarda su desglose en una tabla hija, como instantánea (ADR-004).

Control de seguridad. Solo consultas parametrizadas, comodines de LIKE escapados e IDs UUID v7 no enumerables. RNF-SEC-02 · RNF-SEC-04

open.er-api.com tipos de cambio

El navegador pide los tipos de cambio, los guarda en caché y avisa si están desactualizados o si fallan (D-22, D-51).

Control de seguridad. La respuesta se valida antes de usarla y el backend no hace ninguna petición saliente. RNF-SEC-13 · RNF-SEC-18

Cómo se construyó

Cuatro fases antes del código (análisis, especificación, arquitectura y plan) y después 14 partes, cada una en su sesión, su rama y su PR. Todas siguieron el mismo ciclo.

El ciclo de cada parte

  1. 1

    Plan

    Una sesión nueva lee la nota de traspaso y presenta el plan: objetivo, criterios, ficheros, orden de los tests y riesgos. No se toca código hasta que el responsable del proyecto lo aprueba.

  2. 2

    TDD

    Primero el test con los vectores de la especificación; en el dominio, siempre, con el 100 % de cobertura.

  3. 3

    Revisor

    Un subagente de solo lectura revisa el diff contra la especificación y la seguridad. Los P0 y P1 se corrigen, cada uno con su test.

  4. 4

    Documentación

    Una sola actualización al cerrar: decisiones, diario, trazabilidad y el prompt literal.

  5. 5

    PR y CI

    Una rama y una PR por parte. main solo acepta la PR con todos los checks del CI en verde.

Calidad que se comprueba sola

Nada se integra en main sin el CI en verde. Las reglas de CLAUDE.md marcadas con ⚙ las hace cumplir una herramienta que también tiene sus tests.

El pipeline

6 trabajos, leídos de ci.yml. Abre uno para ver sus pasos.

  1. quality9 pasos
    1. Format
    2. Lint
    3. Typecheck
    4. File names, forbidden patterns and dependency cycles
    5. Migrations match the schema (db:check)
    6. Node tests (domain coverage 100 %)
    7. Web unit tests
    8. Build
    9. Traceability, blocking (every AC and TV has a test; only the declared pending ones are left, D-161)
  2. audit2 pasos
    1. Dependency audit (fails on high or critical, AC-57)
    2. No committed .env files (AC-55)
  3. e2e8 pasos
    1. Start the Compose stack and wait until it is healthy (AC-97, D-133)
    2. Containers without root, read-only, ports on 127.0.0.1 only (AC-60, D-130)
    3. Install Chromium for Playwright
    4. Evaluator walkthrough, published and from file:// (D-183, D-184)
    5. e2e against the Compose stack, real CSP and headers (AC-96, AC-64, AC-52)
    6. Playwright report and traces
    7. Logs of the stack (the API logs carry no personal data)
    8. Stop the stack and delete its data
  4. smoke5 pasos
    1. README · install
    2. README · migrate and seed (npm run setup)
    3. Install Chromium for Playwright (with its system libraries on Linux)
    4. Install Chromium for Playwright
    5. README · start (npm run dev), GET /health and the dashboard with the sample data (AC-95)

Dónde intervine yo

10 momentos en los que mi criterio cambió el rumbo, en el orden en que ocurrieron. El texto es el de ai-workspace/README.md; cada uno enlaza con su decisión y con el prompt en el que lo pedí.

  1. 01

    1. Validación fiscal estricta

    Rechacé la validación genérica de 2 a 20 caracteres fuera de España: no es «estricta». Pedí el formato oficial de cada país, con su fuente, y un validador por país detrás de una interfaz común.

    D-15 · prompt

  2. 02

    2. Seguridad con método

    Pedí sustituir el requisito de seguridad genérico por un bloque basado en el OWASP API Security Top 10 y un modelo de amenazas, incluido por qué no hay login.

    D-40 · prompt

  3. 03

    3. Un fallback que no esconde el error

    Aprobé la caché de los tipos de cambio con una condición: carga, error con «Reintentar» y tipos desactualizados se ven siempre, cada estado con su e2e.

    D-51 · prompt

  4. 04

    4. La CSP, comprobada

    Pedí verificar si el build de Angular inyectaba CSS en línea, y un e2e que falle ante cualquier violación de CSP. Con el valor por defecto, la política habría dejado la web sin estilos.

    D-70 · prompt

  5. 05

    5. El flujo de trabajo

    Decidí una rama y una PR por parte, y hooks rápidos (el lint del fichero editado, nunca el build completo). Tras el primer NO APTO del revisor acepté su propuesta: npm install <paquete> y gh pr merge pasaron a pedir confirmación.

    D-80, D-82 y D-85 · prompt 07 y prompt 08

  6. 06

    6. La IP real, sin atajos

    Exigí que los proxies de confianza fueran solo loopback y la subred de Docker de la demo, nunca todos los rangos privados; en P6 estreché el de la demo a direcciones exactas y pedí un e2e que demuestre que una IP falsa no abre un cubo nuevo del límite.

    D-113 y D-130 · prompt 13 y prompt 18

  7. 07

    7. El diseño, una extensión de roams.es

    Pedí que la interfaz pareciera una extensión natural de la web de la empresa, roams.es: misma familia visual, no una copia. Validé la maqueta con dos ajustes.

    D-122 · 10-diseno-visual · prompt
